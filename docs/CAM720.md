# CAM720 (Jooan JA-A12) in Home Assistant

The TV room's camera is a Jooan JA-A12 (CAM720 app, W8-U on the label).
Home Assistant drives video, pan/tilt, Wi-Fi setup and two-way talk directly
over the camera's LAN protocols. Jooan's cloud is used once per camera, to
read a hidden token, then permanently blocked at the router.

## Protocols

The camera speaks four protocols on the home network:

| Port | Protocol | What we use it for |
|---|---|---|
| 80  | HTTP `/goform/...` CGI | Wi-Fi setup, settings read/write |
| 554 | RTSP (login required) | live video and listen-in audio in HA |
| 8899 | ONVIF (no login) | pan/tilt |
| 32761 | TUTK Kalay DTLS (UDP) | two-way talk |

The HTTPS tunnel the camera and the CAM720 app use to reach Jooan's cloud
(`use1api.jooaniot.com`, Alibaba IoT MQTT) is **not** used by Home Assistant
and gets blocked at the router after setup.

## Stream names

RTSP paths observed on this firmware (version 84025200):

- `rtsp://192.168.1.144:554/live/ch00_0` — lens 1 (bottom bunk), 2304×1296 H.264.
- `rtsp://192.168.1.144:554/live/ch00_1` — lens 1 sub, 640×360.
- `rtsp://192.168.1.144:554/live/ch01_0` — lens 2 (top bunk), 2304×1296 H.264.
- `rtsp://192.168.1.144:554/live/ch01_1` — lens 2 sub, 640×360.

Both streams carry G.711 A-law audio from the camera's microphone at 16 kHz.
Audio _to_ the camera (talk-back) goes over DTLS, not RTSP.

## Two-way talk — the DTLS story

Two-way talk goes over the ThroughTek Kalay protocol: UDP on port 32761,
wrapped in DTLS 1.2 with pre-shared key (`TLS_PSK_WITH_AES_128_CBC_SHA256`).
The PSK is derived like this:

```
PSK = SHA256( device_pwd )
```

`device_pwd` is a 14-character password that Jooan's cloud generates once
per camera and stores in the camera's flash. It is:

- Returned to signed-in CAM720 app / web clients in
  `POST /api/vms/device/v3/query_device_list` →
  `device_info_list[*].jooan_info.properties.device_pwd`.
- **Deterministic per hardware.** Observed stable across delete+rebind
  (one session), full factory-reset + rebind (another session), and across
  multiple days: three independent captures returned the same value.
- Never exposed over any plain-HTTP endpoint on the camera itself. Every
  `/goform/getDeviceInfo` call we tried returned `error_passwd`, meaning
  the HTTP admin password Jooan sets at bind-time is also an opaque value
  held only by their cloud.

So the one-time setup needs Jooan. After that, we hold the token and the
cloud is dead weight.

### Extracting `device_pwd`

1. Install mitmproxy on the Athan Hub and run it as an HTTP proxy on port
   18080, listening on all interfaces (not transparent):
   ```sh
   sudo systemd-run --unit mitm mitmdump --listen-host 0.0.0.0 --listen-port 18080 \
     --mode regular --showhost -w /root/mitm/flow.mitm --set confdir=/root/mitm
   ```
   The CA cert ends up at `/root/mitm/mitmproxy-ca-cert.pem`.

2. On any Windows machine (CrossOver or Parallels is fine; mobile apps pin
   their own certs so iOS/Android are no use), trust the CA and set the
   system proxy to `192.168.1.210:18080`:
   ```powershell
   certutil -addstore -f "Root" "C:\path\to\mitmproxy-ca-cert.pem"
   netsh winhttp set proxy 192.168.1.210:18080
   Set-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' -Name ProxyEnable -Value 1
   Set-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' -Name ProxyServer -Value '192.168.1.210:18080'
   ```

3. Install and run the CAM720 Windows app (also called `CAM720VmsTools.exe`,
   from Jooan's PC download page). The desktop app does not pin, so the
   proxy sees everything.

4. Sign in. The app calls `/api/vms/device/v3/query_device_list` and the
   response carries `device_pwd`. On the Hub, read it back from the flow:
   ```python
   from mitmproxy import io, http
   import json
   for flow in io.FlowReader(open("/root/mitm/flow.mitm", "rb")).stream():
       if not isinstance(flow, http.HTTPFlow): continue
       if "jooan" not in flow.request.pretty_host: continue
       if "query_device_list" not in flow.request.path: continue
       for d in json.loads(flow.response.get_text() or "{}").get("device_info_list", []):
           if d.get("uid") == "<CAMERA_UID>":
               print(d["jooan_info"]["properties"]["device_pwd"])
   ```

5. Drop the token into `/etc/athan-hub/athan-hub.env`:
   ```
   ATHAN_HA_CAMERA_P2P_TOKEN=<14 chars>
   ```
   Do not commit it, do not print it in chat. Everything that needs it reads
   from this file.

6. Clean up the Windows VM:
   ```powershell
   netsh winhttp reset proxy
   Set-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' -Name ProxyEnable -Value 0
   certutil -delstore "Root" "mitmproxy"
   ```
   Then stop and uninstall mitmproxy and delete `/root/mitm/`.

## go2rtc patch

The Kalay DTLS code in [AlexxIT/go2rtc](https://github.com/AlexxIT/go2rtc)
targets Wyze cameras, which derive the DTLS PSK differently. The CAM720
patch is three lines:

```go
// pkg/tutk/dtls/auth.go
func DerivePSK(input string) []byte {
    hash := sha256.Sum256([]byte(input))
    psk := make([]byte, 32)
    copy(psk, hash[:])          // CAM720 does not truncate at NULL
    return psk
}
```

And one line in `pkg/tutk/dtls/dtls.go` for the cipher:

```go
config.CipherSuites = []dtls.CipherSuiteID{dtls.TLS_PSK_WITH_AES_128_CBC_SHA256}
```

The patched binary gets dropped onto the Hub in place of the one that the
WebRTC Camera integration downloads at install time.

## What is _actually_ on the camera

Decoded from the Android APK (`com.jooan.qiaoanzhilian.fmr.gp`, 5.4.2.11):

- `/system/bin/avapi` is the ThroughTek Kalay runtime.
- `security_password` (visible in `query_device_list`) is the camera's AP-mode
  Wi-Fi password, nothing to do with DTLS.
- `/goform/setAPLanP2PAuthkey` sets a different key still, used only in AP
  mode. Confirmed: setting this via HTTP does **not** change `device_pwd`.
- `avClientRequestChangeServerPassword` (TUTK IOCTL) is the only API that
  changes `device_pwd` in flash. It needs an authenticated DTLS session, so
  we need the current token to change it.

## Firewall / blocking

Pi-hole alone is not enough: the camera has hard-coded Kalay broker IPs
(`130.49.180.138`, `158.101.97.20`, `130.61.112.25`, …) that bypass DNS.
Full air-gap requires a device-level block on the BT Hub against MAC
`74:33:36:AD:C5:D1`.

After the block, these keep working:

- Pan / tilt (ONVIF, LAN only).
- Live video and listen-in (RTSP, LAN only).
- Two-way talk (Kalay DTLS, LAN only).
- Remote access via Tailscale (we tunnel to the Hub, Hub reaches the
  camera on LAN).
- The HA script "Camera Wi-Fi setup" (CGI call to the camera's AP-mode HTTP).

What stops working:

- CAM720 app on your phone outside the home.
- Firmware updates from Jooan.
- Push notifications from Jooan (we did not use them).

## Protocol work in progress

Everything after DTLS auth needs the TUTK AV session format that CAM720 uses,
not the Wyze flavour the upstream code targets. A fresh session should pick up
here:

1. **IOCTRL framing.** The upstream `pkg/tutk/dtls` `msgIOCtrl` wraps the
   payload in Wyze's variant: 16-byte outer with `protoVersion`×2 and `avSeq`,
   then IOCtrl at offset 16. CAM720 ACKs it but does not act. The standard
   Session16 wrapper (28-byte header `04 02 1d 0a | size-16 | 00 00 | 07 04 21 00 |
   sid16` + 24-byte cmd header `00 70 0b 00 | seq | ... | ts`) is implemented
   as `(*DTLSConn).WriteIOCtrlStd(ctrlType, body)` in the local fork, but the
   camera does not stream video on `IOTYPE_USER_IPCAM_START` (511) with
   `SMsgAVIoctrlAVStream{channel=0, option=0}` either. The IOCtrl is reaching
   the camera (ACKs seen) but the right pattern to make it push frames is
   still to be found.
2. **Audio frame format.** Upstream `msgAudioFrame` is Wyze-shaped (16-byte
   outer + inner chunk header, `tutk.ChannelAudio=0x03`). CAM720's native
   `avSendAudioData` wraps the PCM/A-law payload with
   `AVFrame.parseFrameInfo(sampleRate, flags=0x12, frameNo, timestamp)` (16
   bytes of frame info) and streams on the main AV channel, not through a
   reverse DTLS backchannel. The right port is to add a `cam720AudioFrame`
   helper that mirrors `AVFrame.parseFrameInfo`, builds a Session16-style
   frame body (`01 03 0b 00 | seq | mediaSize | 00 00 | 28 00 | size | msgId
   | 01 00 00 00 | payload | ODUA 20 00 00 00 | frameInfo`) and writes it via
   `c.clientConn.Write`.
3. **ClientDTLSChannelNew needs the identity.** The CAM720 handshake uses PSK
   identity `AUTHPWD_admin`. Our Dial sets `PSKIdentityHint`, pion sends it,
   the camera accepts it. Keep this if any further changes are made.

The local fork lives at
`~/Downloads/cam720-apk/go2rtc-src/AlexxIT-go2rtc-7c05066/` with
`pkg/cam720/` for the producer and the Session16 IOCtrl patch in
`pkg/tutk/dtls/conn_dtls.go`.

## Open questions

Written down so a future session can pick them up.

1. **Is `device_pwd` derivable from the UID and MAC?**
   If so, Home Assistant could set up a brand-new CAM720 end-to-end
   without ever touching Jooan.
   - Known inputs: UID `EB6JNB3YN64E12TK111A`, MAC `74:33:36:AD:C5:D1`.
   - Known output: 14-character `device_pwd` (not committed; see env file).
   - One data point is not enough for a derivation hypothesis. Two or
     three cameras would settle it.

2. **Can port 9898 return the token?**
   The Windows app queries `http://<camera>:9898/get?singleCMD=get_deviceFeatures`
   during AP-mode setup. The port opens and closes depending on camera state.
   We saw it listening after a reboot but not during normal operation. Needs
   a reset to probe again.

3. **Does the camera have a factory default `device_pwd` before cloud bind?**
   The code path for first-time cloud contact is in `libAVAPIs.so`, around
   the `IKalayAVNew` family. If the camera uses a baked-in default before
   it writes the cloud-assigned value to flash, we could skip Jooan with
   `cam720-provision` on a fresh unit.

4. **CAM720 app sharing.** The Jooan app has "share with family" that
   generates a QR code. If the QR contains `device_pwd` or the auth info,
   that is another extraction path that doesn't need the Windows app.

5. **ChangeServerPassword.** Available over authenticated DTLS. Could be
   used to rewrite `device_pwd` to a value we pick, so Jooan's copy becomes
   stale. Not needed in practice but closes the "Jooan knows my token" gap.
